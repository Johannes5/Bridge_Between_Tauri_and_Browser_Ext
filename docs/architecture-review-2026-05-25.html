Candidate 1

Envelope Handler Registry

Strong
Files
packages/app-tauri/src/store.ts packages/ext-plasmo/src/background.ts packages/sidecar/src/main.rs
Problem

The Zustand store has a 360-line switch statement dispatching on envelope.type. Adding a new message type means editing the main loop. The sidecar has the same problem in Rust. This is the worst kind of shallow module: the interface (the dispatch map) and the implementation (every handler) live in the same place with no seam between them. Delete the switch and complexity explodes across every caller — which proves it earns its keep as a registry, not a monolith.

Solution

Extract a typed handler registry: registerHandler(type, handler) / dispatch(envelope). Each handler is its own module. The registry is the seam — you can swap implementations, test handlers in isolation, and add new message types without touching anything else.

Benefits
  • Locality: Each handler owns its own change surface — a new tabs.pin handler lives in one file
  • Leverage: Callers only need dispatch(envelope) — zero knowledge of type strings
  • Testability: Register a mock handler in tests; dispatch envelopes and assert state changes
Before
store.ts (360 LOC)
├─ switch(envelope.type)
│  ├─ case "tabs.list"     // 40 LOC
│  ├─ case "tabs.delta"    // 60 LOC
│  ├─ case "presence.status" // 20 LOC
│  ├─ case "browser.info" // 15 LOC
│  └─ case "focus.window" // 25 LOC
│       ...8 more cases
│
└─ No seam. Adding a type
   means editing this file.
After
handlers/
├─ tabs-list.ts        // isolated
├─ tabs-delta.ts       // isolated
├─ presence-status.ts  // isolated
└─ ...

registry.ts
├─ registerHandler(type, fn)
└─ dispatch(envelope)      ← seam

store.ts (30 LOC)
└─ import * from handlers/
   registry.dispatch(env)
Candidate 2

Tab Delta Merger Module

Strong
Files
packages/app-tauri/src/store.ts packages/ext-plasmo/src/background/delta-manager.ts
Problem

Tab reconciliation (applying added/updated/removed deltas onto a snapshot map) is 100+ LOC of inline logic inside the Zustand store. Meanwhile, the extension has its own delta accumulator. Both ends deal with the same conceptual problem — "merge a delta onto a tab map" — but there's no shared, tested abstraction. The deletion test passes: delete this logic and its complexity reappears in every component that needs to display current tab state.

Solution

Extract applyDelta(snapshot: TabMap, delta: TabsDelta): TabMap as a pure function module in shared-proto or a new shared-logic package. The interface is the test surface: give it a snapshot and a delta, assert the result. No Chrome APIs, no Tauri, no Zustand.

Benefits
  • Locality: All tab-merge bugs concentrate in one module
  • Leverage: Both extension and app can import the same logic; no drift
  • Testability: Pure function — trivial to test with property-based tests
Before
store.ts
└─ applyBrowserDelta(...)
   // inline: for each added...
   // inline: for each updated...
   // inline: for each removed...
   // 100+ LOC, side-effectful

delta-manager.ts (extension)
└─ separate accumulation logic
   (different impl, same concept)
After
shared-proto/src/delta.ts
└─ applyDelta(
     snapshot: TabMap,
     delta: TabsDelta
   ): TabMap           ← pure fn

store.ts
└─ applyBrowserDelta(id, delta)
   // 5 LOC: call applyDelta

delta-manager.ts
└─ imports applyDelta too
Candidate 3

Browser Detection Module

Worth exploring
Files
packages/sidecar/src/main.rs (detect_browser) packages/ext-plasmo/src/background/state.ts packages/ext-plasmo/src/background/utils.ts
Problem

Browser identity is determined in at least three places: the sidecar inspects parent process names via sysinfo; the extension reads UA strings and environment; state.ts stores the result alongside connection state. These are two separate detection strategies with no shared source of truth. When a new browser appears (Arc, Zen), you update multiple files.

Solution

Sidecar: extract a detect_browser(process_name: &str) -> BrowserName pure function. Extension: extract detectBrowser(): BrowserName with a single UA-matching lookup table. Separate browser identity from connection state in state.ts.

Benefits
  • Locality: Adding Arc/Zen browser means editing one lookup table, not hunting through two runtimes
  • Testability: Pure function; test every browser variant with a table of process names → expected output
  • Leverage: All callers get a typed BrowserName — no string comparison elsewhere
Before
sidecar/main.rs
└─ detect_browser()
   // sysinfo parent walk
   // string matching scattered

state.ts (extension)
└─ browser: BrowserInfo
   // set during handshake
   // UA parsing inline

No shared contract between them
After
sidecar/browser.rs
└─ detect_browser(process: &str)
   → BrowserName          ← seam
   // CHROME, FIREFOX, ARC...

ext/background/browser.ts
└─ detectBrowser(): BrowserName
   // UA lookup table only

Both use shared BrowserName enum
from shared-proto
Candidate 4

Connection Lifecycle Module

Worth exploring
Files
packages/app-tauri/src/store.ts (startListening) packages/ext-plasmo/src/background.ts (connect) packages/sidecar/src/main.rs (ws loop)
Problem

Reconnect logic, backoff, and "is connection ready" state are duplicated across the extension and the sidecar. The store's startListening() is 50+ LOC that mixes event subscription, error recovery, and presence tracking. One adapter = hypothetical seam; here there are two or three ad-hoc implementations, which means the seam is real but currently implicit.

Solution

Extract a ConnectionManager with a clear lifecycle interface: connect() / disconnect() / onStatusChange(cb). The manager owns backoff, keeps status: "connecting" | "connected" | "disconnected", and exposes an observable status. The store only subscribes to status changes.

Benefits
  • Locality: All reconnect bugs live in ConnectionManager
  • Leverage: startListening shrinks from 50 LOC to 5
  • Testability: Inject a mock ConnectionManager — test the store's reaction to disconnect without real WebSockets
Candidate 5

Configuration Module

Speculative
Files
packages/app-tauri/src-tauri/src/bridge_ws.rs packages/sidecar/src/main.rs
Problem

Port numbers (17342, 17888) are hardcoded in both Rust and TypeScript. A user running two instances, or a developer switching environments, has no way to override this without recompiling. Not a critical friction point today, but will become painful as the project grows.

Solution

Extract a config.rs / config.ts that reads from env vars with compiled-in defaults. Shallow change, but concentrates the configuration surface.

Top Recommendation

Start with the Envelope Handler Registry

The 360-line switch statement in store.ts is the single biggest architectural liability. It makes every new message type a risky edit, and it's impossible to test handlers in isolation. An envelope registry is a small interface (two functions) with enormous leverage — it turns a monolith into a plugin system. This is the kind of change that makes the codebase feel immediately more AI-navigable: an agent can reason about handlers/tabs-delta.ts without loading 300 lines of unrelated handler code into context.

After the registry, the Tab Delta Merger is the natural second step — it cleans up the largest handler and makes the reconciliation logic reusable across runtimes.
